# 클래스 로딩

> 태그: `#java` `#jvm` `#classloader`<br>
> 작성일: 2026-06-26<br>
> 최종 수정일: 2026-06-26

## 정의

클래스 로딩은 JVM이 클래스 파일을 찾아 메모리(Method Area/Metaspace)에 적재(Loading)하고, 검증·준비·해석(Linking)을 거쳐 초기화(Initialization)하는 전체 과정이다.

## 특징 / 상세

### 부모 위임 모델 (Parent Delegation Model)

3단계 계층 구조다.

- Bootstrap: JDK 핵심 모듈(`java.base` 등)을 네이티브 코드로 로드. `getClassLoader()`로 조회하면 `null`이 반환된다.
- Platform: `java.base` 외 JDK 플랫폼 모듈.
- Application(System): 클래스패스/모듈패스의 애플리케이션 클래스.

클래스로더가 클래스를 찾으라는 요청을 받으면, 먼저 부모에게 위임하고, 부모가 (그 부모까지 재귀적으로) 못 찾았을 때만 자신이 직접 찾는다. 핵심 클래스를 애플리케이션 코드가 같은 이름으로 갈아치우는 걸 막기 위한 동작이다.

이건 JVMS가 강제하는 알고리즘이 아니라 `java.lang.ClassLoader`의 기본 구현 동작이다. 커스텀 클래스로더는 이 위임을 깨고 직접 로드할 수도 있다(OSGi, WAS의 webapp별 클래스로더 등).

### 클래스 동일성 — (binary name, defining loader)

JVM에서 클래스/인터페이스의 동일성은 이름만으로 결정되지 않는다. **이름과 정의 클래스로더(defining loader)의 쌍**으로 결정된다.

같은 `.class` 바이트코드를 클래스로더 A, B가 각각 로드하면 Method Area(Metaspace)에 별개의 `Class` 객체 두 개가 생긴다. 결과:

- 클래스로더 A가 만든 `Class` 객체와 B가 만든 `Class` 객체는 `==`로 다르다.
- A로 로드한 클래스의 인스턴스를 B로 로드한 같은 이름의 타입으로 캐스팅하면 `ClassCastException`이 난다.

이 때문에 WAS(Tomcat 등)는 애플리케이션(webapp)마다 별도 클래스로더를 둬서 서로 격리한다 — 같은 이름의 클래스를 여러 앱이 각자 다른 버전으로 가져도 충돌하지 않게.

### Linking — Verification / Preparation / Resolution

1. **Verification**: 바이트코드의 바이너리 표현이 구조적으로 올바른지 검증한다. 실패 시 `VerifyError`.
2. **Preparation**: static 필드를 만들고 기본값(`0`, `null`, `false`)으로 초기화한다. 바이트코드 실행이 전혀 없는 단계다 — 명시적 초기화식과 `static { }` 블록은 여기서 실행되지 않는다.
3. **Resolution**: 런타임 상수 풀의 심볼릭 참조를 실제 참조로 해석한다. 구현에 따라 "lazy"(쓰일 때마다 개별 해석)나 "eager"(검증 시점에 한꺼번에 해석) 전략 중 선택 가능.

```java
public class Counter {
    static int count;      // Preparation 단계에서 0으로 채워짐 (바이트코드 실행 없음)
    static { count = 10; } // Initialization 단계에서 실행됨 (<clinit>)
}
```

### Initialization — 트리거 4가지와 상수 인라인 예외

클래스/인터페이스 T는 다음 중 하나가 처음 일어나기 직전에 초기화된다.

- T가 클래스이고 T의 인스턴스가 생성될 때
- T가 선언한 `static` 메서드가 호출될 때
- T가 선언한 `static` 필드에 값이 대입될 때
- T가 선언한 `static` 필드가 사용되는데, 그 필드가 **상수 변수(constant variable)가 아닐 때**

```java
public class Constants {
    public static final int MAX = 100; // 컴파일 시점 상수 → 상수 변수(JLS §4.12.4)
}

public class Caller {
    void use() {
        int x = Constants.MAX; // Constants 클래스를 초기화하지 않는다
    }
}
```

`static final int MAX = 100;`처럼 컴파일 시점 상수식으로 초기화된 필드는 JLS 기준 "상수 변수"가 되고, `javac`가 참조하는 쪽 바이트코드에 값 `100`을 그대로 인라인한다. 런타임에 `Constants`에 대한 심볼릭 참조 자체가 생성되지 않으므로 초기화 트리거도 없다.

실무 함정: 라이브러리의 `static final` 상수 값을 바꾸고 라이브러리만 재배포하면, 그 상수를 참조하던 코드가 재컴파일되지 않은 한 컴파일 시점에 인라인된 옛 값을 계속 쓴다.
